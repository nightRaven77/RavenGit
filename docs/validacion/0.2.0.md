## Funciones de este incremento

1. Navegación entre Historial y Cambios sin perder el borrador en la misma apertura.
2. Listas separadas de archivos preparados y sin preparar.
3. Diff por archivo y selección de bloques para preparar o quitar de preparados.
4. Preparar/quitar archivos completos, incluidos nombres Unicode, espacios, saltos de línea y nombres que Git podría interpretar como pathspec.
5. Commit normal y primer commit, con resumen/descripción y autor configurado en Git.
6. Confirmación de habilitación de operaciones locales por apertura del repositorio; sin cambios de configuración de confianza global.
7. Borrador conservado al fallar un commit y aviso del hash tras éxito.

Es un avance de RG-03 y parte del trabajo diario previsto en M2. No se declaran cerrados M0, M1, M2 ni el MVP completo: las validaciones de plataforma, rendimiento y accesibilidad siguen pendientes.

## Controles implementados

Las escrituras de RavenGit se serializan. El staging se realiza en un index temporal dentro de una carpeta exclusiva, bajo el lock del index principal. Se comprueban HEAD, rama, index, estado y contenido/permisos de archivos modificados antes de operar. El staging vuelve a comprobarlos antes de instalar el index. Los bloques exigen además que coincida la huella del diff mostrado, incluso si cambió la configuración de agrupación de bloques.

Los comandos reciben argumentos separados y rutas literales; no se usa shell ni se acepta un parche arbitrario del frontend. El commit utiliza Git con sus hooks y configuración de firma. Los hooks y filtros pueden modificar archivos y no se promete revertir sus efectos. Ante timeout o resultado incierto, el mensaje pide comprobar HEAD antes de repetir.

Esto no equivale a aislamiento completo frente a programas externos que cambien refs o ignoren locks. Evita operaciones Git paralelas mientras se crea un commit. Tampoco es una sandbox para hooks.

## Límites y próximos pasos

No hay amend, descarte, checkout, merge/rebase visual, clone/fetch/push, cuentas, APIs, workspaces persistentes ni paneles redimensionables. Los archivos nuevos, binarios, eliminados o con cambios de modo se preparan completos; el staging parcial se limita a modificaciones de texto regulares.

Se bloquean para escritura submódulos, repositorios anidados, split index, HEAD separado y operaciones/conflictos en curso. Se mantiene lectura cuando es compatible. La búsqueda sigue limitada a commits cargados, y el diff no está virtualizado. Límites: 2 MiB de salida de lectura y 64 MiB por archivo modificado para la huella; UTF-8 requerido. Los límites no se presentan como benchmarks.

Próxima validación prioritaria: abrir la aplicación nativa, usar un repositorio de prueba, preparar un bloque, crear commit y comprobar el resultado en el grafo. Después: rendimiento y accesibilidad; luego ampliar operaciones avanzadas con recuperación. La licencia pública, remoto y publicación siguen pendientes de elección del usuario.

## Reproducir

```sh
npm run build
npm test
cargo test --manifest-path src-tauri/Cargo.toml --offline
cargo clippy --manifest-path src-tauri/Cargo.toml --offline --all-targets -- -D warnings
npm run tauri build -- --debug --bundles app
```

Ejecutar las comprobaciones Rust y el empaquetado de forma secuencial. En una copia nueva, quitar `--offline` para descargar dependencias. Para revisar únicamente el diseño: `npm run dev` y abrir `/dev/changes.html`; esa página es un fixture y no pertenece al build de aplicación.

Documentación primaria consultada: [git-status](https://git-scm.com/docs/git-status), [git-apply](https://git-scm.com/docs/git-apply) y [git-commit](https://git-scm.com/docs/git-commit).
