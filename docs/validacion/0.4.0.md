# RavenGit 0.4.0 — publicación normal con revisión

Fecha: 20 de octubre de 2026. Incremento de desarrollo; no constituye aceptación completa del MVP.

## Resultado y alcance

Vista «Publicar» integrada con Historial, Cambios y Remotos. Selección explícita de remoto, rama local y rama del servidor; el nombre de destino puede ser distinto del local. Se utiliza la URL efectiva de publicación, incluso si difiere de la URL de descarga. No se configura automáticamente ningún remoto del proyecto RavenGit ni se publica su código durante esta validación.

Al entrar sólo se lee configuración local. Revisar contacta con el destino y, cuando falta su commit, descarga los objetos necesarios sin refspec de destino, con refmap vacío, sin etiquetas ni escritura de FETCH_HEAD. No hace checkout ni cambia archivos o índice. Se comprueba de nuevo el tip del servidor para detectar cambios durante la comparación.

La revisión distingue rama nueva, al día, adelantada, atrasada o divergente. Se muestran el número total de commits locales ausentes de la rama de destino, el número por integrar y hasta 200 hashes/mensajes. Es una comparación de alcance del historial, no una estimación de objetos/bytes transferidos. Una rama nueva incluye todo su historial alcanzable aunque el servidor ya posea algunos objetos.

La confirmación requiere confianza por apertura y una revisión que Rust mantiene en memoria, ligada al repositorio, URL, fuente, destino, configuración y referencias. La UI sólo devuelve el identificador de revisión; no envía un refspec ejecutable ni una nueva URL al confirmar. La revisión se consume antes de ejecutar, también si falla. Cambiar campos, actualizar o salir de la vista descarta la revisión de la UI; abrir otro repositorio elimina la guardada en Rust.

La publicación usa un único refspec completo cuyo origen es el hash revisado. Push normal sin force, mirror, tags, borrado ni recursión de submódulos. Atraso y divergencia impiden confirmar. Si la rama, configuración, refs o tip remoto cambian antes de ejecutar, se requiere una revisión nueva. No hay push automático ni reintentos.

## Seguimiento y resultados

Seguimiento opcional y explícito sólo cuando descarga/publicación tienen la misma URL efectiva y configuración estándar. Después de que Git informe éxito se consulta el servidor para confirmar el hash. Sólo entonces se intenta establecer el seguimiento. Git puede actualizar referencias remotas locales como parte del push; no se confunde esa actualización esperada con un cambio de configuración externo.

La actualización de seguimiento usa comparación de la referencia anterior y después configura upstream. No es una transacción indivisible: puede quedar parcial. Un fallo produce una advertencia junto al éxito del push y nunca invita a repetirlo para reparar configuración local. Si Git termina sin poder confirmar el destino, se informa de la incertidumbre y no se cambia upstream.

Hooks y reglas del servidor se respetan. La firma de push configurada en Git se conserva; no se validó un flujo de firma real. Errores de acceso/rechazo se muestran con mensajes controlados que evitan exponer stderr con datos sensibles; el detalle de diagnóstico puede requerir Git. Leer el destino no prueba permisos de escritura. Las caídas de conexión o timeout pueden dejar un resultado incierto; consultar el servidor antes de revisar otra vez. Sin retries.

## Restricciones deliberadas

Publicación bloqueada para remotos avanzados/heredados, varias URLs, mirrors, refspecs especiales o configuración con reglas de reescritura `insteadOf`/`pushInsteadOf`, incluso si una regla no afecta aparentemente a ese destino. Evita que una URL ya resuelta se reescriba otra vez entre consulta y envío. No se modifica esa configuración para habilitar push.

Clones shallow/parciales, grafts, conflictos y operaciones Git pendientes no permiten publicar en esta fase. La comparación usa objetos reales sin reemplazos Git. Se conserva el mecanismo no interactivo de credenciales/SSH existente, TLS y hosts conocidos; no se introducen cuentas OAuth ni almacenamiento de tokens.

Se serializan las operaciones de RavenGit y la apertura de repositorios. El push vuelve a comprobar el repositorio activo y su autorización dentro de ese bloqueo. Persiste una ventana frente a cambios externos entre comprobación y operación de red; esto no es un bloqueo distribuido ni una garantía de coincidencia exacta del tip durante toda la conexión. Git y el servidor aplican sus comprobaciones normales de avance directo y actualización de refs. Una carrera puede dar rechazo o un avance directo permitido por el servidor; no se promete semántica de lease ni se usa force-with-lease.

Límite por proceso: 15 s local, 60 s de conexión y salida de 2 MiB. La revisión puede ejecutar varias consultas; estos límites no son un timeout total de la interacción. Hooks y helpers de repositorios autorizados ejecutan código; el proceso no ofrece aislamiento de scripts.

## Validación ejecutada

- Rust: 44 pruebas aprobadas, incluidas 13 nuevas de push con repositorios temporales y servidores bare locales. Sin conexiones a proveedores reales.
- Frontend: 25 pruebas aprobadas, incluidas 10 nuevas de Publicar, mediante IPC simulado.
- TypeScript/Vite: compilación aprobada.
- Clippy: sin advertencias.
- Revisión visual en navegador de selección, comparación y confirmación con datos sintéticos; la fixture rechaza toda publicación real.
- Compilación de desarrollo nativa macOS arm64: aprobada mediante `npm run tauri build -- --debug --bundles app`; bundle RavenGit.app generado (32,41 MiB).

Los escenarios Git cubren rama nueva y upstream, avance directo sin publicar etiquetas/otras ramas, al día/atraso/divergencia, URL de publicación diferente, revisión obsoleta por cambios locales/configuración/servidor, rama nueva que aparece después de revisar, confianza, validación de nombres, operaciones pendientes, destinos reescritos/múltiples, rechazo de hooks locales/servidor, fallo de upstream tras push confirmado, descarga de historial ausente sin cambiar refs/FETCH_HEAD y bloqueo de clones parciales/shallow.

Las pruebas de UI cubren entrada sin contacto automático, revisión sin publicación, confirmación con token, invalidación por cambio de destino, divergencia, confianza, upstream explícito, destinos distintos, rechazo sin retry conservando entrada y advertencia de seguimiento separada del éxito.

## Pendiente

Autenticación y publicación HTTPS/SSH con GitHub, GitLab, Gitea propio y Bitbucket en repositorios de prueba; prueba nativa de extremo a extremo, Windows y Linux, accesibilidad integral, historial de 100 000 commits y distribución firmada/notarizada. Git LFS, hooks complejos y certificados corporativos requieren validación específica. La compilación y la fixture no sustituyen estas pruebas.

Siguiente incremento propuesto: integrar cambios con merge y resolver conflictos con continuar/abortar; después rebase. Pull compuesto, force push, borrado remoto y administración avanzada de upstream permanecen pendientes de diseño/implementación.
